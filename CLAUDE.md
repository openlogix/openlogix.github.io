# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The main website for the Open Logix organization, a static GitHub Pages site served at `www.openlogix.org`.

## About Open Logix

Open Logix builds easy-to-use open source tools for FPGA design. Site content should present these projects as one ecosystem:

- **Logix Engine** is the core of the ecosystem. It is an MCP backend that gives frontends FPGA services: building, testing, simulation, verification, and board programming. Every other project runs on top of it.
- **Logix Catalog** (motto: "Every FPGA board, described once.") is the open catalog of FPGA boards: each board's FPGA, how to program it, and what its pins are wired to (clocks, LEDs, buttons, headers), one JSON file per board. Logix Engine downloads the catalog release its remote config names, the `logix-catalog` package (about 30 KB, before the tools), and serves it to everyone else (see the next point); nothing is built in (decided 2026-11-10). Contributors add and fix boards in the `logix-catalog` repo, never in the engine repo. Its design is in progress (added 2026-11-08).
- Frontends, each serving a different level of design and implementation:
  - **Logix IDE**: an Arduino-like experience for FPGAs.
  - **Logix CLI**: a command-line tool, inspired by Apio.
  - **Logix VSCode**: an extension for VS Code.
  - **Logix Studio**: a graphical, schematic-based design tool.
  - **Logix Remote**: a network adapter for remote FPGA development.
  - **Logix AI**: a set of AI agents that design and test FPGA logic and program the board.

- **All access to the catalog goes through Logix Engine** (decided 2026-11-08). The rule, for Open Logix's own code: every Open Logix product, script and AI agent, at runtime or build time, gets board and FPGA data only through the engine's API (`get_catalog` and the tools built on it), never from Logix Catalog's files. The one exception is the catalog's own maintenance in the `logix-catalog` repo: its checker, importers, tests and CI read and write the files directly. For everyone else, the engine's API is the intended, supported interface. It isn't enforced: the data stays free to use and copy under its license, and reading the files directly is at the reader's own risk (their layout may change). Public wording says "intended", never "allowed" (the catalog's READMEs, its product page, the overview deck). Why: one version of the data (the one the engine builds and programs with), custom boards read and checked the same way, facts the engine derives (toolchains, pin file kinds, variant labels) in one place, and freedom to change the files' layout. The board file format stays public for writing boards (custom boards and catalog contributions), with the stability that implies after the first release; reading is the engine's job. What a tool needs from the catalog that the API lacks is added to the engine (Engine first), and scripts reach it through the engine's command line.
- **AI hints in board data** (decided 2026-11-09). Logix Catalog boards and their resources may have `ai_hints`: short lines of free text, mainly for AI agents writing designs for the board, only for what the structured data can't express (first use: the iCE40 UltraPlus boards whose RGB LED needs the FPGA's RGB LED driver). Always the last field of its board or resource; advice to weigh, not instructions. Logix Engine returns them unchanged in `get_catalog`; Logix IDE's Board Explorer shows them. The catalog's `docs/model.md` (AI hints) owns the details.
- **Each frontend owns its project model and examples.** The engine takes explicit inputs (folders, files, board) and has no project files or examples, so each frontend uses the project model and source format that fit it best (IceStudio's block diagrams have no `.v` sources, for example) and ships examples in that format. Frontends on the engine don't depend on Apio. Logix CLI is only inspired by Apio: not close to it and not compatible with it, in its project model or its commands (decided 2026-11-08).

- **Long-term goal: libraries** (raised 2026-11-08, not decided). Frontends should one day support libraries: reusable design code users add to their projects, the way Arduino has libraries. Open is where they live: possibly a new product, such as Logix Libs, that defines libraries once for every frontend (as Logix Catalog does for boards), if a shared format can serve frontends with different project models; otherwise each frontend defines its own. Nothing is built or promised yet: the overview deck lists it as a longer-term goal (Logix Lib), with remote development (Logix Remote), hardware-in-the-loop testing (Logix HIL) and training material and media; site pages don't mention Logix Lib or Logix HIL.
- **Milestones** (decided 2026-11-10; Logix Engine's `docs/requirements.md`, Acceptance and phasing, owns the details): 1, the engine's proof of concept (done); 2, Logix IDE running on the engine, on macOS; 3, Logix Engine and Logix IDE on Windows x64; 4, the same on Linux x64; then more boards and more hosts (Logix CLI, Logix Studio and others).
- **Diagnostic features, and a local engine (recommended for all frontends).** By default a frontend uses only the GitHub package of the engine release it pins, or, with remote updates, the one its remote config names. Diagnostic and debug features of the frontend or the engine, turned on at runtime, may change that. They aren't meant for normal use by end users: they're for Open Logix developers, for users an Open Logix developer guides through them, and for manual and automated testing of Open Logix components. The convention for running a frontend on another engine binary is the environment variable `LOGIX_DEV_ENGINE_BINARY`, the path to a `logix-engine` executable (such as one built from a local engine clone). A frontend that follows it honors it in every build, whether run from a local checkout or installed from a GitHub-built package (a stable release is a pre-release declared stable, the same binary, so a build-time switch can't tell them apart); gives that engine its own engine folder, so the regular engine's packages are never touched; shows that it's in use for the whole session, not only in a log; and treats a value that isn't an executable file as an error, never falling back silently. The engine doesn't read the variable and no one can enforce it, so it's a recommendation, followed so every frontend works the same way. Each frontend's repo says how to use it (Logix IDE: `scripts/run.sh --engine-repo-dir <engine clone>`, or the variable itself).
- **Development never affects end users** (the user's requirement for Milestone 2, 2026-11-12). What Open Logix developers do to develop and test (a remote config change, a new release of a dependency, a local build, a dev engine) must never change what end users' installed products do until it's deliberately released. So a remote config change is tried with the override (`LOGIX_<COMPONENT>_DEV_REMOTE_CONFIG`, pointing at a pull request's branch, a fork or a local file), never by changing the file on `main`, which every installed product reads; it reaches users only by a pull request merged into `main` with its CI green. Diagnostic settings are off unless a developer sets them, and nothing a developer runs writes to a place end users' products read (such as a repo's `main` or its releases) outside that flow. On a developer's own machine, isolation isn't required: dev and regular builds of a product share its data folder (`~/.logix/<program>/`), settings and projects (the user's preference).
- **Remote updates** (the design agreed 2026-11-12; part of Milestone 2; built 2026-11-12 for the engine and Logix IDE with one config file per version, then extended the same day with channels, being built; modeled on Apio's remote config). Goal: a user who installs a product gets newer releases of its dependencies without a new release of the product, automatically or on request, and is never blocked when offline.
  - **Versions and tags** (decided 2026-11-12): every component's version is its release date. Its forms: `yyyy-mm-dd` (`2026-11-20`) is the tag: release tags, pins, a remote config's `release`, receipts; `yyyymmdd` (`20261120`) only in release file names (`logix-engine-darwin-arm64-20261120.tgz`); `yyyy.mm.dd` (`2026.11.20`, as Apio) is the version people see (`--version`, `get_engine_info`, About and System Info, release titles, docs); semver (`2026.5.7`, the version without leading zeros) only where a tool requires it (`Cargo.toml`, `package.json`, `tauri.conf.json`), written by the build and never shown. At most one release a day per repo: no `yyyy-mm-dd-N`. (Log file names and `BUILD-INFO.json`'s build time hold dates but aren't versions.)
  - **A folder per config version** (decided 2026-11-12): `remote-config/<product>/<NNN>/` in the product's own repo, such as `logix-ide/remote-config/logix-ide/001/`. Each component hard-codes its config version as a three-digit string (`"001"`, zero-padded so folders sort; the first is `001`) and reads only that folder. It's internal: shown only for diagnostics (`get_engine_info`, Logix IDE's System Info, `config-version` in each release's `BUILD-INFO.json`). Each version folder is self-contained: its files' formats and names concern only the releases of that version, so a new version may change any of them without touching older installs. The version goes up by one only when a new release can't share the current folder (it needs a dependency release a file there can't offer, it adds or drops a dependency, a file's format changes, or updating a file would break older releases that read it). Old folders stay, so older installs keep working and can still get updates. Not a date (it would look like a release tag). A folder per product, so a repo could hold several. JSONC, so each entry carries a comment saying why it changed. Changed only by pull request. Today's version folder holds `channels.jsonc` and one config file per channel in use, `<channel>.jsonc` (`prod.jsonc`, `dev.jsonc`).
  - **Channels** (decided 2026-11-12, to keep development from affecting end users): a release reads the config file of its *channel*. `prod` is what users get; `dev` is the default, for every release a version's `channels.jsonc` doesn't list (all daily builds, and local builds, which have no release with their tag); more channels (such as `beta`) can be added later as a key in `channels.jsonc` and a config file, with no program change. `channels.jsonc` (its schema `logix-channels-v1.json`) maps channel names to explicit release tags, no ranges (a range would promote untested builds), e.g. `{"$schema": "...", "prod": ["2026-11-20"]}`; it lists only releases of its own config version, and each release is on at most one channel. A component learns its channel at runtime: its own version (its release tag) looked up in its version folder's `channels.jsonc`, read and cached with the config (24 hours, used offline), so the same binary moves to `prod` when it's promoted, with no rebuild. Each component picks its own channel, so the channel follows through dependencies by itself (a prod Logix IDE's `prod.jsonc` names a prod engine release, which reads the engine's `prod.jsonc`). **A channel without its own file uses `prod.jsonc`** (decided 2026-11-12): in normal maintenance there's no `dev.jsonc`, and dev builds use exactly what users get; when dev needs something else (a new engine or core under test), a `dev.jsonc` is added by pull request, and deleted again once a promotion has caught prod up. The fallback is a rule, not an error, and it's shown ("dev, using the prod config" in System Info and `get_engine_info`); an unknown channel name is an error. A version folder must have `prod.jsonc`, or, until that version's first promotion, `dev.jsonc` (which is then required: `prod.jsonc` appears with the first promotion). **Local builds are always dev** (no release has their tag; a local build's version is today's date, which could match a prod tag), unless `LOGIX_<COMPONENT>_CHANNEL` says otherwise; a build knows it's a release build because the release workflow passes it the release tag. **Tests** (daily and on pull requests) run once per config file in the newest version folder, from the checkout (so a pull request is tested with the pins it changes): `prod.jsonc` alone in normal maintenance, and `dev.jsonc` too while it exists.
  - **Dev and prod are independent of the stable flag** (decided 2026-11-12): whether a release is *prod* (on the `prod` list) is set only by promotion; GitHub's *stable* flag only means kept forever and eligible for Latest. A prod release must be stable (CI and the janitor fail otherwise); a stable release may be dev (a *stable dev* release, kept, such as one handed to testers; never Latest). An installable repo's Latest must be a prod release. The possible states (Local: a local override is needed for it):

    | # | Stable | Prod config | Prod | Local | Comments |
    | :---: | :---: | :---: | :---: | :---: | --- |
    | 1 | | | | | Normal daily dev build. The default. |
    | 2 | X | | | | A stable dev build: kept, such as one handed to testers. Still dev, and never Latest. |
    | 3 | X | X | X | | Normal production release. The default for prod. |
    | 4 | | X | | X | A dev build tried against what users get. Still dev. |
    | 5 | X | X | | X | Row 2, pointed at the prod config. |
    | 6 | X | | X | X | A prod release pointed at the dev config, such as to check it with new dependencies. Still prod; other users are unaffected. |

  - **Promotion** (decided 2026-11-12): per repo, independently, by people: test the pre-release (dev channel, or locally against the prod config, row 4), mark it stable on GitHub, then add its tag to the `prod` list of its version's `channels.jsonc` by pull request, and repin the `prod.jsonc` files that should use it, also by pull request; a prod config names only prod (stable) releases of other components, which CI checks. Remote choices (the files on `main`, the channel lists) are the only way to change what users get. A `promote` workflow in `openlogix/.github` may automate the steps later.
  - **Where a component finds its files** (decided 2026-11-12): each component hard-codes two values, its repo (`openlogix/logix-ide`) and its config version (`"001"`); the rest follows the org rule, the same for every component: the folder `remote-config/<product>/<NNN>/` (`<product>` is the component's package name), on `main`, its files read raw from GitHub, `https://raw.githubusercontent.com/<repo>/main/<path>` (as Apio). So CI can check that each component's current folder and files exist, and changing the hosting is one rule change.
  - **Local overrides** (decided 2026-11-12, as Apio), per component, since a user may mix components from different repos; each component reads only its own, and a program it starts (Logix IDE starts the engine) inherits the variables: `LOGIX_<COMPONENT>_CHANNEL` (`LOGIX_IDE_CHANNEL`, `LOGIX_ENGINE_CHANNEL`; no `DEV_`, since `dev` is a channel name, and it's a runtime setting) picks the channel instead of `channels.jsonc`; `LOGIX_<COMPONENT>_DEV_REMOTE_CONFIG` (`LOGIX_IDE_DEV_REMOTE_CONFIG`, `LOGIX_ENGINE_DEV_REMOTE_CONFIG`) reads the version folder from elsewhere: an `https://` URL of a folder, such as a pull request's on its branch or a fork, or a local folder. Both are local choices: they affect only the machine where they're set and never change a release's status (dev or prod). They follow `LOGIX_DEV_ENGINE_BINARY`'s conventions: read at startup, honored in every build, shown for the whole session (a banner, System Info, `get_engine_info`), and a bad value (an unknown channel, a folder without that channel's file, an unreachable URL, a file that fails its schema) is an error, never a silent fallback. Receipts record the URL, so going back to the regular files downloads again what differs.
  - **Its content:** `$schema` (`https://www.openlogix.org/schemas/logix-remote-config-v1.json`, owned by `openlogix/.github`, with a copy in this site's `docs/schemas/`; `channels.jsonc` names `logix-channels-v1.json` the same way), then one entry per direct dependency, keyed by its package name, with one key per line: `repo` (`owner/name`), `release` (the release's date tag) and `file` (the release asset's name, a template with `${PLATFORM}`, such as `darwin-arm64`, and `${YYYYMMDD}`, the tag without dashes). For example, `"logix-catalog": { "repo": "openlogix/logix-catalog", "release": "2026-11-24", "file": "logix-catalog-${YYYYMMDD}.tgz" }`.
  - **CI** checks each config file against its schema (and `channels.jsonc` against its own), that every named release and file exists, that prod files name only stable releases and every listed prod release is stable, that each release is on at most one channel, and that the newest version folder's files name exactly the dependencies the product's source on `main` expects. A change is tested as a pin change would be: the component's tests run with the releases it names (for the engine, that the catalog fits the core, and its build tests) before it merges. CI also refuses repos outside `openlogix` on `main` (a test branch may name a fork, tried with the override above).
  - **Stable releases in prod configs only** (decided 2026-11-12): a `prod.jsonc` names only prod releases, which are stable (never deleted); a `dev.jsonc` may name pre-releases, which stay as long as a config names them (Release cleanup). `check-remote-config` requires stable releases in prod files. Built 2026-11-12: `repos-janitor`, a workflow in `openlogix/.github` (every 6 hours) that checks across repos (remote configs, stale pins, rebuilt releases, schema copies, daily runs, releases, Latest, repo types) and reports problems, as Apio's janitor does; fixes, such as repins, come later. `openlogix/.github`'s `CLAUDE.md` owns its design.
  - **No "withdrawn" list:** a product always moves to exactly what its file says, so a rollback is a pull request that restores the previous release.
  - **Direct dependencies only:** each component manages only its own: Logix IDE its engine and examples (a new `logix-ide-examples` package), Logix Engine its core and catalog. Data packages (catalog, core, examples) have none.
  - **Asking a dependency to check its own:** a component may ask a direct dependency that is a program with its own remote config (today only the engine) to check its dependencies, through its API (the engine's `check_updates` tool), never its files. It's a request with no releases or files in it: the dependency decides from its own config and receipts, and passes the request one level on if it has program dependencies of its own. `check_updates` ("check now") checks, downloads and switches in one call.
  - **When to check** (decided 2026-11-12, as Apio): each component caches its remote config and fetches it again when the cached copy is more than 24 hours old, or when asked. Before every operation that uses its dependencies, it compares them with the cached config (by their receipts) and downloads or repairs on the fly whatever is missing, broken or out of date, so an operation may wait for a download (as PlatformIO's do). Updates apply at the start of an operation, never in the middle of one. Always automatic: no opt-out setting for now. The engine follows it too, on its own (decided 2026-11-12): never at startup, only before an operation, with every update reported in the operation's progress and result (its rule became "no unreported upgrades"); `--no-auto-download` turns it off. So its host needn't ask it every 24 hours, and the engine on its own (AI agents) stays current.
  - **What the user is told** (decided 2026-11-12): downloads show progress ("Downloading logix-catalog 2026.11.24…"); after an update, one line in the operation's output or status bar, with friendly names for data ("Updated the boards and FPGAs to 2026.11.24") and product names for programs ("Logix Engine 2026.11.20"); nothing when nothing changed, and nothing offline unless the user asked to check (the product keeps working with what it has); a failure that blocks an operation is an error with the reason and what to do ("Couldn't download the FPGA tools: no network connection. Connect and try again."). Logix IDE's System Info and the engine's `get_engine_info` list every dependency's release and the config version.
  - **Receipts:** next to each downloaded dependency, its receipt: `repo`, `release`, `file`, `url`, `platform`, `size`, `sha256`, `downloaded_by` (the program and its version, such as `logix-engine 2026.11.20`, for diagnostics) and `layout` (a number the program raises only when it changes how it lays packages out). A dependency is present only if its folder exists and its receipt matches the config: the URL, the platform, the SHA-256 the release's `SHA256SUMS` gives (which catches a release rebuilt under the same tag) and the layout. Not the program's version (decided 2026-11-12): the SHA-256 already proves the bytes, so a program update reuses packages that are still right. Any mismatch: download it again.
  - **The flow** (a Logix IDE release on config `001`): it reads its folder `001/` (`channels.jsonc`, then its channel's config file); downloads the engine and the examples, unless their receipts match; starts the engine and calls `check_updates`; the engine reads its own folder by its own config version and channel, downloads core and catalog unless their receipts match, and uses them from the next operation. Offline, each component uses its cached files and the packages it has. **No built-in pins** (decided 2026-11-12, as Apio): the config files in the repo are the component's pin lists, and its tests read them (the dev file); a first start needs the network anyway, to download the packages. The engine on its own (AI agents) works the same from `check_updates`.
  - **Dropped dependencies and cleanup:** only a new config version drops a dependency, by leaving it out of its files, which comes with a product release. After it has its current config file's releases in place, a component deletes everything in its dependencies folder that the file doesn't name (dropped dependencies, old releases of kept ones). Deletion follows ownership: deleting the engine's folder takes the core and catalog the engine downloaded with it, and Logix IDE never touches them itself. Going back to an older product version downloads what it needs again.
  - **Release cleanup** (decided 2026-11-12; separate from dev and prod): each repo's own build deletes its old pre-releases (the shared `publish-pre-release` action, with only its own repo's token): a pre-release is deleted only when no remote config file on `main` in any Open Logix repo names it (any version, any channel; read from the public files) and it isn't among the newest kept (`actions/release-policy.sh`, today 5). Stable releases are never deleted. A `dev.jsonc` is deleted by pull request when it's no longer needed (dev falls back to prod); prod files are never deleted once their version has users. During initial development (no backward compatibility), old releases and old config files that no longer match the current model are deleted right away, without waiting for anything that still refers to them. `repos-janitor` only reports (such as a dev file no release can read), and never deletes.
  - **Switching to a new release** (decided 2026-11-12, kept simple, close to Apio): download it into a temporary folder, check its SHA-256, unpack it, put it in place and delete the old release. A failure is a setup error for that operation, and the next one tries again; there's no "last working set".
  - **Idea: messages in the remote config** (TODO, raised 2026-11-12, after the Windows and Linux ports; not decided). A remote config could also carry information for its component and the component's users (other components, people, AI agents), not only its dependencies: such as a notice that a newer version of the product is out (with where to get it), a known problem and its workaround, or a note for an AI agent using the engine. Open questions: the shape (likely a separate top-level key with message entries, so dependency entries stay as they are), who each message is for and how each kind of user is shown it (UI line, `get_engine_info`, MCP instructions), targeting by product version, wording rules for user-facing text, and a new schema version (`logix-remote-config-v2`) with CI checks.
- **Environment variable names.** `LOGIX_<COMPONENT>_<PURPOSE>_<NAME>`: `LOGIX_` alone only for a convention several components follow (today only `LOGIX_DEV_ENGINE_BINARY`); otherwise the component that reads it (`LOGIX_ENGINE_`, `LOGIX_IDE_`, and so on for later products), then `BUILD_` (read only when building), `TEST_` (tests only), `DEV_` (development setups and scripts), or nothing for a setting the shipped program reads at runtime; then the name, saying what it holds (`FOLDER`, `BINARY`, `VERSION`). Examples: `LOGIX_ENGINE_BUILD_VERSION`, `LOGIX_IDE_TEST_ENGINE_FOLDER`, `LOGIX_IDE_HOME`. Each repo lists its own in its `CLAUDE.md`. Add one only when an argument or a script option won't do.

- **Logix IDE is the reference frontend.** Much of a frontend's logic, such as choosing boards and board variants, showing what's connected, choosing a device, Upload, build reports, problems and the console, is the same for every frontend, and frontends may come from anyone, inside or outside Open Logix. Two ways keep it from being rewritten each time:
  - **Engine first:** logic every frontend needs, that doesn't depend on a frontend's own model (its project files, examples or look), goes into Logix Engine, without breaking its abstraction (requests stay explicit and stateless). When a frontend repeats engine knowledge, such as FPGA family names or the toolchain's resource names, that's a gap to fill in the engine.
  - **An example to follow:** Logix IDE's AI spec (its `CLAUDE.md`), docs and code, public under MIT or Apache 2.0, show how to use the engine; the engine's tool API, which stands on its own for any frontend, links to the IDE files that implement each recipe. The IDE uses only what the tool API documents, so what works for it works for anyone.
  - **Easy to explore:** the IDE repo's content (code, docs, AI spec and the parts of it about the engine) is written for easy exploration by people and AI agents who develop hosts and frontends, inside and outside Open Logix: clear names and layout, each part's purpose and its engine calls explained where they are, and nothing that needs Open Logix's private context to understand.

- **Wording: the engine downloads tools, it doesn't install them** (decided 2026-11-09). Logix Engine downloads its toolchain packages into its own engine folder and runs them; nothing is installed on the system. So say "downloads" (the engine downloads and runs open source tools), never "installs", for the engine's packages and tools, in the engine's API (`download_packages`, `auto_download`, `--no-auto-download`, package status `ready`), its MCP instructions, frontends' setup messages, docs and pages. "Install" stays for what is really installed: an app or extension (installing Logix IDE), drivers, and other software (Rust, Claude Code). "Nothing to install" for users stays true.
- **Wording: never "Logix" alone** (decided 2026-11-10). "Logix" is short for Open Logix, the whole project, so it never stands alone for a product, and even for the project the full name is preferred: write "Logix IDE", "Logix Engine" and so on in full everywhere (site pages, docs and their site names, READMEs, UI messages, release notes, code comments, AI specs), and "Open Logix" for the project ("every Open Logix tool"). Exceptions: the OpenLogix wordmark, a product name split by markup ("Logix <span>IDE</span>"), the name itself in the license's "don't call it Logix" lines, and file and folder names (`~/.logix`, `logix-ide.toml`, `~/Documents/Logix`).
- **Folder names** (the user's rule, 2026-11-10): no spaces in folder names (in repos, and folders the products create, such as a default projects folder); separate words with `-`, such as `logix-ide`. Prefer lowercase when possible and reasonable, except in the OS's standard user folders (such as `~/Documents` on macOS), where a product's folder follows the OS's own capitalization, as its neighbours do. **Data folders** (decided 2026-11-10): every Open Logix program keeps its data (settings, logs, scratch, its own Logix Engine folder with the FPGA tools) in its own lowercase folder in `~/.logix`, on every OS: `~/.logix/ide/` for Logix IDE, `~/.logix/claude-code/` for the engine tutorial's Claude Code setup, `~/.logix/engine-dev/` for the engine's dev scripts, a script's own (such as `~/.logix/scripts/`). Hosts never share an engine folder. `~/.logix/README.txt` (written by Logix IDE when missing) says what each folder is and that deleting one is safe. No migration of older layouts. **Projects folders** (decided 2026-11-10): every Open Logix product that keeps its own projects puts them in one shared parent in the OS's documents folder, `~/Documents/OpenLogix/` (the wordmark: no space, and not "Logix" alone), in a subfolder named by the product's short name in its own spelling: `IDE` for Logix IDE (`~/Documents/OpenLogix/IDE/<project>/`), `Studio` for Logix Studio, and so on. Products that work in the user's current folder (Logix CLI, Logix VSCode) have none. Project folders inside are the user's own names; generated folders inside a project start with `_`. Temporary and generated (artifact) folders inside a user's project folder start with `_`, such as `_build`, so they stand apart from the user's own files. Names a tool or a convention fixes (`README.md`, `LICENSE-MIT`, `.github`, `CLAUDE.md`) stay as they are.
- **No backward compatibility during initial development** (the user's rule, 2026-11-10): no code, fallbacks or notes that keep old names, formats or folders working, in any repo (the engine's API, file names, settings, folders). Change the thing and its users in one go; the user deletes old local files by hand.
- **Wording: no file sizes** (the user's rule, 2026-11-11): user-facing text (docs, READMEs, pages, release text, UI messages) doesn't give file or download sizes, such as "about 3 GB". Why: they may change at any time (a new tool release, a new package), and they're hard to track and keep up to date across every page that mentions them, so they go stale. Say what something is and, where it helps, that it's large or small ("the first start downloads the FPGA tools, which takes a few minutes"). Limits the software enforces, such as a log cleanup's maximum, aren't sizes in this sense.
- **Wording: program boards, not FPGAs.** Most users program an FPGA board, not a bare FPGA chip, so say "program the board" or "program FPGA boards", never "program FPGAs" or "program the FPGA". This applies everywhere: site pages, product descriptions, repo descriptions, READMEs, docs and release notes. Logix IDE's motto, "The Arduino experience, for FPGAs.", is not about programming and stays as it is.

## Canonical board

The **iCESugar v1.5** (iCE40 UltraPlus UP5K, by Muse Lab; [github.com/wuxx/icesugar](https://github.com/wuxx/icesugar)), catalog ID `icesugar-1-5`, is the canonical board of every Open Logix product and repo (decided 2026-11-10). It replaces the Alhambra II, the de facto canonical board during early development (it came with Apio).

- **Why.** We compared six candidates (the iCESugar v1.5, iCEBreaker, Alhambra II, iceFUN, Olimex iCE40HX8K-EVB and Tang Nano 9K) on price, availability, open source tool support, programming, drivers, power, connectors and documentation (a comparison page, `docs/canonical-board/`, deleted once the board was chosen). The iCESugar v1.5 won on: low cost (about $32 with its programmer on board, against $70 to $80 for the iCEBreaker and Alhambra II); no driver to install on any OS (its on-board iCELink programmer is a standard USB device); four PMOD connectors, so add-on modules need no wiring; the mature, reliable open source iCE40 toolchain; and easy to buy worldwide (AliExpress, Amazon, Tindie). It's also powered and programmed over one USB-C cable, has a UART to the computer over the same cable, and a public schematic and maker examples built with open source tools.
- **Where it's used.** Examples, proofs of concept, showcases, demos, tutorials, and docs that need an example board: the iCESugar v1.5 unless the material is about another board. Existing material moves to it as it's updated. The Logix Engine tutorial (`docs/tutorial-claude-code.md`) moved to it on 2026-11-11, before the team had the board; its prompts are still to be tried on one.
- **Used, not publicized.** Nothing public (site pages, READMEs, docs, release notes, decks, social posts) says it's our canonical, preferred, recommended or default board, and we don't promote or sell it: we just use it. The AI specs (`CLAUDE.md` files) may name the rule, since they're how contributors and agents learn it.
- **Products stay neutral.** No feature, ordering, matching, search result or wording favors it over other boards. It may only break a tie, where something must be chosen and nothing else decides, such as the board a new user starts with.
- **The best-described board.** Logix Catalog's `icesugar-1-5` gets extra effort to be as complete and accurate as possible, from its schematic, its maker's files and hardware tests.
- **Each repo applies it** in its own `CLAUDE.md` (what it uses the board for), pointing here for the rule.

## Org principles

Every Open Logix product follows these principles. Site content should reflect them consistently:

- **Easy:** products are intuitive and easy to install and use.
- **Self-contained:** products bundle everything they need, so users never have to install a toolchain separately.
- **Cross-platform:** products support macOS (ARM), Windows (x64), and Linux (x64).
- **Free and open:** every product is 100% free and open source, built by community members for the community, under the permissive MIT or Apache 2.0 license, the user's choice. Adapted versions just can't use the Logix name. The site stresses this on purpose (hero badge, "No catch" section) to answer "what's the catch?" doubts. Keep that message prominent, and don't add anything that suggests paid tiers or upsells.
- **Experienced team:** the team are experienced developers from the US and Europe, with more than 40 years of combined professional software development and a long track record in the open source movement. The site uses this to build trust, as the "40+ years" figure in the "No catch" section.
- **Spec-driven:** each product is built from a detailed AI specification. This makes changes, adaptations, and new features quick and low-effort.
- **Quality and trust:** products have extensive automated tests. All code is public, every release is built on GitHub, and builds are reproducible, so users can build it themselves. The site presents this positively ("Transparent and verifiable") to build trust. Don't use words like "malware" or "virus" on the site.
- **AI-native engine:** Logix Engine is MCP-compatible. Off-the-shelf AI systems can use it to generate code and testbenches, then lint, build, simulate, and program the board, with no other software needed.

Until stable releases are required, having no Latest passes. **Latest is for people who install it, not for the products that use it** (the user's rule, 2026-11-12): an installable repo's Latest is the release recommended to someone installing it directly, and it's independent of the release another product's remote config names. The latest Logix IDE may install an engine release other than the engine's Latest (for example, the engine's Latest is 2026-12-01 for people setting it up for an AI agent, while Logix IDE's config still names 2026-11-20 until it's repinned after testing). It's a dependency because its releases can be dependencies of components inside or outside Open Logix, even when no remote config in the org names one today. Policy: the releases a remote config names must exist (later, be stable) and be in the current release structure; its release text carries the "Use it through Logix Engine" note where that applies. **Its Latest** (decided 2026-11-12): we'd rather have none, but GitHub always marks one Latest once a repo has a stable release, so it must at least mean something: it's the newest release that the recommended installs use, the latest one cleared for public release through the Open Logix installables. Precisely: for each installable repo's Latest release, the dependency releases it uses are the ones its remote config names (its `prod.jsonc`, in the version folder its `config-version` in `BUILD-INFO.json` names, on `main`: an installable's Latest is a prod release), directly or through another installable it names (Logix IDE's Latest names an engine release, whose own config names a core and a catalog; that engine release need not be the engine's Latest). These are the dependency's *reachable* releases; its Latest should be the newest of them, by date. Two installables can reach different releases of a dependency (their Latest releases on different config versions): that's fine, both stay (stable, never deleted), every install still gets what its own config names, and Latest is only for people who download the dependency directly, for whom the newest release a recommended install uses is the best one. While the newest reachable release is a pre-release (as during development), it can't be Latest yet, and having none, or an older stable one, passes. A Latest no recommended install reaches is a warning. Nobody decides a dependency's Latest by hand: `repos-janitor` computes it, says which release to mark Latest (with a link) and lists in its report which recommended install uses which release.

- **Wordmark:** "Open" in regular weight and muted color, followed by "Logix" in heavy weight, with no space between them (`OpenLogix`). It always sits next to the logo tile.
- **Org logo:** a 3x3 grid of logic cells (a nod to FPGA fabric). The cells forming an "L" are solid white and the rest are faint. The tile uses the brand gradient, indigo `#6366F1` to cyan `#06B6D4`, which is also the site's accent color.
- **Product icon recipe.** Every family icon follows this so they read as a set:
  - `viewBox="0 0 64 64"`, a `rect` with `rx="16"` as the tile, filled with a diagonal linear gradient (top-left to bottom-right) from a light shade to a deep shade of the product's own hue.
  - One simple white glyph, centered within roughly 14 to 50. Draw it with `stroke="#fff" stroke-width="4.5"`, round caps and joins, and no fill. Small solid white accents (dots, triangles, stars) are allowed.
  - Current hues: Engine violet, Catalog red, IDE green, CLI slate, VSCode blue, Studio orange, Remote cyan, AI pink to purple. A new product needs a hue that isn't taken yet.
- Glyphs: Engine = chip, Catalog = open book, IDE = window with a play button, CLI = `>_`, VSCode = `</>`, Studio = AND gate, Remote = wireless signal, AI = sparkle.
- **Slide decks** (decided 2026-11-08): every Open Logix slide deck follows one style, and the overview deck (`docs/overview/`) is the baseline: 16:9 slides on a dark backdrop, white content slides with a light title slide, titles at the same height with their last part in the brand gradient, bold-led bullets, the small logo bottom left, "‹ n / m ›" bottom right, and share and full-screen buttons top right. New decks link the shared stylesheet, `docs/assets/deck.css`, and reuse the overview deck's markup and script, rather than copying or restyling them; a change to the look is made there, for every deck.

## Open decisions

- **How people contact the team, and which GitHub features each repo uses** (TODO, raised 2026-11-08). Decide the recommended ways to reach Open Logix (such as GitHub issues, Discussions, email, or a chat server) and which repos turn on issues, Discussions, wikis and Projects, if any; then say it on the site and in the repos' READMEs, and turn the rest off. Today (2026-11-08) every repo has issues on; Discussions are on only in `logix-ide`; wikis and Projects are on in every repo except `logix-ide` (GitHub's defaults, never decided); the site names no way to contact the team.

- **FPGA families and toolchains** (decided 2026-11-08; applied in logix-catalog, logix-engine and Logix IDE). People see FPGA **families**, the names on the chips and their datasheets: iCE40, ECP5, GW1N (LittleBee), GW2A (Arora), GW5A (Arora V), Artix-7, Spartan-7 and Zynq-7000. A family is a fact about the chip, so Logix Catalog has one FPGA file per family, `fpgas/<family>.json` (`ice40`, `ecp5`, `gw1n`, `gw2a`, `gw5a`, `artix7`, `spartan7`, `zynq7000`), whose name gives its FPGAs' family; a board gets its family from its FPGA (`fpga_id`) and never names a family or a toolchain. Facts the family implies (yosys's Gowin family, the Project X-Ray folder) aren't repeated per FPGA: the engine derives them. Logix Engine maps each family to one of four **toolchains**, a single name, not a list of tools: `ice40` (iCE40), `ecp5` (ECP5), `gowin` (GW1N, GW2A, GW5A) and `openxc7` (Artix-7, Spartan-7, Zynq-7000). A toolchain name selects the engine's build flow (`ice40`: nextpnr-ice40 and icepack; `ecp5`: nextpnr-ecp5 and ecppack; `gowin`: nextpnr-himbaechel's gowin uarch and gowin_pack; `openxc7`: nextpnr-xilinx and the openXC7 tools, a separate package), is for logs, diagnostics and the API, and is never the main word people see. Why: the old four "architectures" mixed families (iCE40, ECP5) with vendors (Gowin, Xilinx), and "architecture" and "family" were used for the same thing. Only the engine knows toolchains: the catalog has no toolchain field, since a toolchain is how Logix Engine builds, not a fact about the chip. The one exception is the catalog's FPGA schemas, one per toolchain (`logix-fpgas-gowin-v1.json` and so on), shared by its families, since their files have the same fields (the user's decision, 2026-11-08). (Board files hold no toolchain-dependent values; those are in the catalog's FPGA entries, such as Gowin's `nextpnr_device` and `packer_device`.) Families follow the vendor's datasheet family, with the series (such as iCE40 HX or UP) as an extra field only if needed. We're in initial development, so backward compatibility didn't matter: the engine's tool API now has `family` on FPGA definitions, `get_catalog` `families` (each with its `toolchain`) and a `family` aspect in `compare_boards`, in place of `architecture`.

## Build / deploy

There is no build step, package manager, linter, or test suite. If shared header/footer markup across many product pages gets hard to keep identical, GitHub Pages' built-in Jekyll (`_includes`, layouts) is the planned next step; until then the template above is the rule. Pushing to `main` deploys the site. To preview locally, run `./view.sh [port]` (default port 8000). It serves `docs/` with Python's built-in HTTP server and opens the browser.
